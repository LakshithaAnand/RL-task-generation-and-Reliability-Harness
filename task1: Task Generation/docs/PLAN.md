# Final Game Plan — Task 1: Synthetic Task Generation Pipeline (Terminal-Bench 2.0 / Harbor)

**Thesis:** The pipeline's product is not tasks — it is *verifiable reward with an executable assurance case*. Every accepted task ships with structured, reproducible evidence that it starts unsolved, is solvable by a known-good solution, is traceably aligned between instruction and verifier, rejects plausible wrong solutions, and carries documented residual risk.

## Deliverables

1. **Runnable pipeline + README** with a two-mode demo: **replay mode** (`make demo`, zero API keys — all procedural stages run live; model-generated artifacts such as near-miss patches and baseline-agent attempt patches are committed to the repo and re-applied and re-scored deterministically on the reviewer's machine; the original model-generation process itself is precomputed and cannot be reproduced without a model) and **full mode** (with an API key, the model-dependent stages regenerate fresh). Every Assurance Card labels which evidence is live vs. precomputed.
2. **Three example tasks** in Harbor format, each with a machine-readable Task Assurance Card.
3. **Design write-up** (2–3 pp), written after results exist so it describes real output.
4. **Funnel report:** ~15–20 candidate mutations in → rejects per gate → survivors → 3 curated for spread across repos, mutation families, and difficulty. The actual top-rejecting gate is reported after the funnel runs, not predicted.

## Pipeline — a funnel of gates; a task clears every gate or is discarded

**Stage 1 — Seed selection.** A curated config of 3–5 Python repos plus deterministic eligibility checks each must pass: clean Docker build, green test suite, permissive license, bounded size, recent activity (reduces likely contamination risk). Curation at the seed level, automation at the task level. Repo auto-discovery at scale: described, not built.

**Stage 2 — Metadata-driven mutation and spec.** Apply a small, seeded, reversible defect from a **mutation template library** (boundary flip, deleted call, inverted condition). Each template carries its own metadata: intended behavior, the changed condition, applicable edge cases, and instruction-safe wording. The structured task specification is generated **directly from this template metadata** — no LLM interprets the diff, removing a hallucination point and preventing instructions from leaking exact tests. An LLM may polish the *wording* of `instruction.md` for naturalness, with the spec as ground truth and a leak check confirming no test details appear. The inverse of the mutation is the oracle: a known-good solution, not claimed unique. Over-generate: 15–20 candidates. Reverted-patch mutation (whose intended behavior lives in PR descriptions and would require interpretation) and requirement mutation are designed future extensions, not built.

**Stage 3 — Failure establishment.** Healthy repo runs green → mutation applied → confirm ≥1 pre-existing test flips pass→fail. No qualifying flip ⇒ discard.

**Stage 4 — Harbor assembly.** Write each validated task as a standard Harbor task folder: `task.toml`, `instruction.md`, `environment/` (Dockerfile + broken repo + the repo's ordinary developer tests, which the agent may read and run), `tests/` (the held-out authoritative verifier, supplied by the harness at scoring time), `solution/solve.sh` (the oracle). Scoring tests never enter the agent's environment — the agent cannot edit its own grader. Instructions describe what "done" looks like; never steps, never test details.

**Stage 5 — Verifier synthesis.** The authoritative verifier in `tests/` is a **superset** of what the agent can see: scoring copies of the flipping regression tests, plus **template-driven edge-case tests generated mechanically from the mutation's own metadata** (e.g., a boundary mutation automatically produces below-boundary / at-boundary / above-boundary checks — deterministic, no model), plus tests targeting the planned near-miss categories. An LLM may propose additional tests; these are optional and labeled `llm_proposed` on the card. **Admission rule: every synthesized test must fail on the broken state and pass on the oracle, or it is discarded and logged.** Disclosed caveat: this filter proves *compatibility* with the task, not semantic validity — a stated limitation. Also disclosed: near-miss hardening and the near-miss battery are correlated; novel cheat families remain residual risk.

**Stage 6 — Instruction–verifier alignment.** From the shared spec, confirm every requirement maps to ≥1 verifier check and every check traces back to a stated requirement. Reject on uncovered requirements or unstated checks. Evidence of alignment, not proof of perfect semantic coverage.

**Stage 7 — Solvability gate.** Run through the real harness twice: `harbor run` with the oracle ⇒ reward 1.0, and a no-op attempt ⇒ reward 0. Both required.

**Stage 8 — Integrity audit (the headline evidence).**
- **Deterministic shortcut battery**, run on every task: hardcode the expected output; probe for exposed verifier/oracle files; spoof artifacts; manipulate exit codes; **environment poisoning** (plant a hostile `conftest.py` / fake `pytest` on PATH as a cheating agent would, then verify the reward does not flip). Each probe's result is recorded as **`blocked`, `failed`, or `not_applicable`** — a probe that doesn't apply to a given verifier is never miscounted as blocked. Any `failed` probe ⇒ harden or discard.
- **Near-miss rejection** — *LLM proposes, harness decides*: from a fixed category taxonomy (partial fix, off-by-one, visible-case hardcode, assertion-gaming patch), an LLM instantiates task-specific almost-right solutions; a deterministic runner executes each against the verifier and records the verdict. Report a per-task rejection rate with categories, what slipped through, and limitations. Generated once via API, committed, re-applied and re-scored live in the demo.
- **Harbor's official QualityChecker** as a *precomputed advisory audit* — agreements and disagreements with the executable battery recorded on the card. Executable checks remain the only acceptance gates; the QualityChecker has no authority over acceptance. (Low integration overhead; droppable if it becomes friction.)
- Off the critical path: one **cross-model audit** demonstration (model A proposes exploits, model B attempts them, the verifier decides), precomputed for the write-up.

**Stage 9 — Difficulty + diversity metadata.** Difficulty: one headline label anchored on a small empirical solve-rate from a cheap baseline agent (attempt patches precomputed and committed; re-scoring is deterministic in replay mode; thresholds fixed before seeing results: easy ≥75%, medium 25–74%, hard <25%; model, attempts, and sample-size caveats recorded on the card), with a structural heuristic as cross-check; disagreements recorded, not hidden. Diversity: tag each task on category / skill-type / difficulty and run a coverage check that the set isn't clustered in one cell. Scoped claim: this pipeline targets the software-engineering slice of Terminal-Bench 2.0 — the largest single category; other categories (sysadmin, security, data) require different seed sources, named as the extension path. Embedding-based dedup at volume: described, not built.

**Stage 10 — Task Assurance Card + funnel report.** Collect every gate's evidence into one JSON card shipped with the task: provenance (repo, commit, mutation template, seed), solvability results, spec coverage, verifier-synthesis admissions/discards (template-driven vs. `llm_proposed` labeled), shortcut-battery results per probe (`blocked`/`failed`/`not_applicable`), near-miss results (labeled live vs. precomputed), advisory-audit notes, difficulty with caveats, residual risks. Cards aggregate to portfolio-level coverage, validation, difficulty, and risk summaries — no single "% trustworthy" score. The funnel report ships alongside, including which gate actually rejected the most candidates.

## Scope boundary (Task 1 vs Task 2)

The generator asks: *"is this task hackable by a cheap trick — does passing mean anything?"* — structural, per-task, no trajectories. Task 2's grader asks: *"was this attempt good?"* — semantic, per-attempt, reads trajectories. Fix-vs-workaround judgment and step productivity are deliberately deferred to Task 2, not rebuilt here. Drawing this line on purpose is itself the engineering-judgment signal.

## Build order (one Claude Code prompt per stage; verify each before the next)

1. Repo eligibility checks → 2. Mutation template library + failure establishment → 3. Spec generation from template metadata + instruction generation with leak check → 4. Harbor assembler → 5. Verifier synthesis (template-driven edge tests + admission rule) → 6. Alignment checker → 7. Solvability gate → 8. Shortcut battery with per-probe status + near-miss harness (+ advisory QualityChecker) → 9. Difficulty + diversity tagger → 10. Card writer + funnel report + replay-mode packaging → curate 3 tasks → design doc.

**Governing principle:** every claim ships with its evidence and its caveat. Known-good oracle, not unique solution. Preliminary difficulty, not calibrated. Near-miss rejection over a stated set, not a validated metric. Compatibility-filtered tests, not semantically proven ones. Three excellent tasks, one command, reproducible evidence.

# Justification — why it's built this way, and why it stands out

**Why repo-seeded defect mutation.** Task content comes from four places: human authoring (highest quality, doesn't scale — Terminal-Bench 2.0's 89 tasks each received multiple reviewer-hours of human auditing), issue mining (maximally realistic but brutal filtering yield, finite supply, heavy contamination risk), from-scratch synthesis (unlimited volume but no ground truth anywhere — task, tests, and solution are all LLM opinions with correlated errors), and seeded mutation of real repos (the SWE-smith approach: ~50k tasks from 128 curated repos). Mutation wins because it provides the two hardest things in synthetic generation *for free*: a guaranteed oracle (the inverse of the mutation) and a failure witness (the test that flips). We chose the method whose weaknesses are cheapest to detect and mitigate mechanically — and every stage of the pipeline maps onto one of those weaknesses.

**Why the spec comes from template metadata, not LLM interpretation.** The ground truth of a defect task is the code change itself, and a procedural mutation template already knows exactly what it changed — intended behavior, flipped condition, applicable edge cases, instruction-safe wording. Generating the spec from that metadata removes an LLM interpretation step from the trust chain entirely and structurally prevents instructions from leaking test details. The LLM's only role near the spec is polishing instruction wording, with the spec as ground truth and a leak check behind it. Reverted-patch mutation is scoped out precisely because it would force interpretation back in.

**Why verifier synthesis exists, and why it's template-driven.** Without it, "held-out verifier" is only folder separation — an agent that satisfies the visible dev tests would pass by definition. Template-driven edge-case tests (below/at/above boundary, generated mechanically from mutation metadata) strengthen the verifier with zero model involvement; LLM-proposed extras are optional and labeled. The admission rule — every synthesized test must fail broken and pass oracle or be discarded — means even the verifier's own tests earn their place through executable checks. Disclosed honestly: that filter proves compatibility, not semantic validity.

**Why near-misses are LLM-generated but deterministically judged.** Handcrafting doesn't scale and contradicts the pipeline story; letting an LLM judge would put a model's opinion inside the trust boundary. *LLM proposes, harness decides* keeps the headline number — the near-miss rejection rate — an executed measurement, not a claim. The known weakness (the rate is only as strong as the set; same-family generation has correlated blind spots) is stated up front; the cross-model demo exists precisely to address it.

**Why environment poisoning is in the battery, and why probes carry three statuses.** Test separation stops the agent editing its grader, but the verifier still executes inside a container the agent controlled — so poisoning the grader's tools (fake pytest, hostile conftest) is the realistic remaining attack. Recording each probe as `blocked`, `failed`, or `not_applicable` keeps the card honest: a probe that doesn't apply to a given verifier is never miscounted as a defense.

**Why the QualityChecker is advisory, not a gate.** It's LLM-based and nondeterministic; a pipeline whose thesis is executable, reproducible evidence cannot let a model's opinion accept or reject tasks. As an advisory audit it has low integration overhead, signals ecosystem fluency, and produces a genuinely interesting artifact — where the official LLM checker and the executable battery disagree — which foreshadows Task 2's grader-reliability question.

**Why over-generate and report the funnel.** The guiding principle — 1,000 tasks of which 30 work is worse than 50 reliable ones — is about *shipping* unvalidated tasks and discovering failures during training. Internal rejection is the fix, not the failure: generate ~15–20 candidates, let the gates kill most, curate 3 survivors for spread, and publish candidates-in → rejects-per-gate → shipped, including which gate actually rejected the most (reported, not predicted). A low internal acceptance rate proves the gates have teeth; near-100% reliability of what ships is the point.

**Why only three tasks.** The goal is thinking and validation, not volume. Three tasks across different repos, mutation families, and difficulty profiles — each with full reproducible evidence — is the strongest form of the argument. Scale levers (repo auto-discovery, reverted-patch and requirement mutation, embedding dedup) are documented as the next iteration.

**Why the two-mode demo.** Reviewers must be able to run everything with zero API keys, but near-misses, difficulty runs, and the cross-model audit need models. Replay mode commits the model-generated patches and re-applies and re-scores them deterministically on the reviewer's machine — the verdicts are computed live, while the generation itself is honestly labeled precomputed; full mode regenerates everything. Every card labels live vs. precomputed evidence — designed around the reviewer's experience.

**Why difficulty is labeled but caveated, and diversity scoped.** Five attempts is noisy; fixed thresholds, recorded caveats, and recorded disagreements keep the difficulty labels honest. And rather than pretending the pipeline spans Terminal-Bench 2.0's full breadth (security, sysadmin, data science, more), we claim its largest single category — software engineering — and name the extension path. Stating the limit first converts a weakness into judgment.

**Why the Assurance Card is the centerpiece.** Most pipelines validate tasks somehow; almost nobody ships the evidence as a standard, aggregatable, per-task artifact with residual risks on it. It converts hygiene into a product a client could consume — the whole pipeline in one sentence: *not "I generated tasks," but "I can tell you exactly why each task's reward can be trusted, and where it can't."*

**The closing story:** I generate grounded defects from real repositories, make each task earn admission through executable gates, actively attack its verifier, and ship the evidence — and the remaining uncertainty — with the task.
